# Prepared pre-cutover metadata inventory

This is a review artifact. Do not execute it until the release operator confirms the exact production app URL, private mailbox identity pins, Gmail login/host/TLS settings and source folders. It does not authorise a production connection or a cutover. It never sends mail, changes flags, issues STORE or fetches MIME bodies. It uses EXAMINE, UID SEARCH and UID FETCH of metadata and `BODY.PEEK[HEADER]`; headers and Message-IDs are used only in process memory and are never emitted. Existing MailHelper authentication may perform the separately authorised routine OAuth refresh.

The optional `--config` defaults to `/data/mail-arrival/release-config.php`. It must resolve inside `/data/mail-arrival/`, be owned by the executing user, have mode 0600, and return the private `mail_arrival` configuration array directly. Credential-named fields are rejected; credentials remain in the app's existing saved mailbox connection. The process applies this config in memory, so it can be reviewed before the module is activated. It requires the existing production DeploymentGuard pins and exact configured mailbox/folder identities. For this release, the operator independently verified saved native logins match the pinned mailboxes and Gmail IMAP uses SSL 993 with certificate validation; any mismatch stops the inventory.

After authentication, the script enforces a session-level read-only default on the primary PDO and uses only prepared SELECT queries for matching. It computes one fixed UTC floor equivalent to the native three-day fetch window, captures UIDVALIDITY and UIDNEXT for each configured folder, and fences UID searches at that initial high UID. It fails if a folder has more than 2,500 candidates and fetches metadata in batches of at most 50. It verifies each folder epoch again after its scan and again after the mailbox's complete scan. Any missing UID, invalid Gmail identity, ambiguous native match, invalid legacy target, changed UIDVALIDITY or backward UIDNEXT fails the entire plan. New UIDs after the captured fence are deliberately outside the plan and must be handled by the subsequent incremental scan.

The private JSON plan contains the floor, mailbox IDs, source folder names, UIDVALIDITY, high UID, candidate counts, known `{gmail_id, thread_id}` matches and unknown/draft UIDs. Gmail IDs and UID values are private provider identifiers: capture the plan to a mode-0600 operator-controlled artifact and never print it into a public log or commit it. Raw header values, Message-IDs, subjects, addresses and credentials are absent. Known matches use the existing native raw/generated Message-ID variants within the same mailbox, or the Fiveways legacy Gmail ledger with target and group verification. Ambiguous or missing Message-ID values remain unknown and must not be skipped.

The operator must independently revalidate UIDVALIDITY at the cutover boundary. The inventory is a snapshot, not an atomic lock on the provider. Initialise each folder with its fixed floor, captured high UID, `last_uid=0` and `seeding=true`; prepopulate only validated known identities, then process unknown and deferred candidates through the bounded importer. Never use the high UID as a completed checkpoint to skip unknowns. Preserve and review the private plan and cutover receipts; do not claim new-message delivery or UI visibility from this inventory alone.
